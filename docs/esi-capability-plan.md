## 0. 当前结论与下一步（2026-09-27 修订）

完整复核见 [项目复核与后续实施依据](review-2026-09-27.md)。下文启动流程和模型是目标设计；执行记录中的“已实现”不代表整阶段验收完成。

当前 ESI 解析、索引和审核仍独立于 C 启动路径。能力查询主要反映已有 PDO 句柄；拓扑快照是诊断输出。已复现离线审核漏查主轴目标速度、类型和重复映射，以及未使用合成来源标记的问题。机床用途检查仍晚于配置下发，不能直接把现有报告接成启动开关。

下一步顺序：

1. **N1：修订 ESI 数据证据契约。** 区分原始声明、PDO 推导、未知/缺省和解析修正，保留完整性、警告、解析器版本与摘要；补最小 XML 反例。这是下一次实施范围。
2. **N2：统一功能依赖和审核。** 修复主轴目标/实际速度依赖、数据类型、重复映射与两端设备字典语义差异；缺少 ESI 声明应表达证据不足。
3. **N3：下发前预检。** 机床用途进入审核，拆分扫描/审核/下发阶段；模拟 SDK 验证必需缺项时绝不调用配置下发。
4. **N4/N5：规划与运行发布。** 完成默认/强制映射、约束/DC，然后将审核计划与本次从站实例绑定，整体启动成功后发布能力，最后实机验收。

静态审核使用计划 PDO，不要求先取得已启用 PDO 快照。独立读回仍为可选诊断，保持“尽量不依赖主站做支持性判断”的既定要求。N1/N2 验收前先不接入自动启停判定和动态新增映射。

## 1. 目标与已对齐需求

根据实际接入的从站建立独立的功能能力表：先扫描有序从站清单及设备身份，匹配本地 ESI，在配置下发前由 ESI 与设备规则审核所需 CoE 对象，生成 PDO 计划；主站执行下发，整体启动成功后将功能绑定到具体从站或从站内的轴。

同一个功能可以对从站 A 可用、对从站 B 不可用。调用不支持的功能应返回明确错误，且不能访问无效对象或发送命令。

示例：假设某型号将 `0x6FFF` 定义为“控制从站报警”。A 支持此功能且通信绑定成功，A 可以调用；B 不支持，B 的该功能禁用。`0x6FFF` 只是需求示例，其子索引、数据类型、控制值、作用范围和通信方式必须依据真实设备资料定义，不能视为跨厂商标准。

ESI 的解析可复用开源工具。开源工具输出需要经过适配，才能表达本项目的功能语义及 FPGA 配置要求。

## 2. 实施基线与待确认规则

以下是审核后的建议基线，尚未由实际设备验证的部分须在实施记录中注明。

| 事项 | 建议基线 |
| --- | --- |
| ESI 匹配 | 按 Vendor ID、Product Code、Revision 精确匹配；兼容版本通过显式规则声明，不自动选择相近版本 |
| ESI 来源 | 从本地已导入目录匹配；导入时建立索引和缓存，运行时不依赖网络下载 |
| 必需功能 | 根据机床配置和轴用途确定；缺失时阻止机床运行并报告 |
| 可选功能 | 下发前依据匹配的 ESI、默认 PDO 和已验证设备规则决定；证据不足或不支持则禁用并记录诊断，不用主站报错试探 |
| ESI 信息不全 | 标记为信息不足；不能在配置前通过 SDK 在线查词典。必需功能信息不足则阻止启动，可选功能保持禁用，直到取得经验证的设备规则 |
| 实时功能 | 第一版通过 PDO 实现；不在实时函数内自动退化为阻塞式 SDO 操作 |
| SDO 功能 | 若需运行期使用，提供明确的非实时接口及请求管理，不与 PDO 函数隐式混用 |
| 映射变更 | 保留设备默认及强制 PDO；新增条目仅用于设备资料明确允许且已验证的映射方案。配置失败是整次启动失败，关闭并重新初始化主站 |
| 重连 / 重启 | 原实例绑定与能力状态失效，重新识别和验证；第一版不承诺运行中热插拔自动恢复 |
| 未配置的从站 | 扫描结果中保留；是否允许继续启动由机床拓扑策略确定，不静默丢弃 |
| 无 CoE 设备 | 扫描及描述模型保留这类设备；不强制要求每台从站都有 CoE 字典，按支持的固定 PDO 路径评估 |

待实施前明确的业务项：各用途的必需功能清单；首批设备范围；是否需要第一版运行期 SDO 功能；拓扑不符时的处理策略。

## 3. 启动流程

1. 初始化主站，进入 SDK 允许扫描和配置的状态。
2. 扫描从站数量、位置及身份，形成独立的从站实例清单。
3. 将扫描结果与机床期望配置核对，匹配 ESI 和设备功能定义。
4. 汇总每台从站及各轴所需的功能，解析其对象依赖和通信要求。
5. 在配置下发前用 ESI、设备规则和机床需求审核对象与映射约束；信息不足按功能必需性处理。
6. 以 EEPROM / ESI 默认映射和强制 PDO 为基线生成配置；仅对有明确依据的功能添加映射，检查容量与冲突。
7. 将规划结果转换为 GreeMaster 的 `Slave_info`，计算布局并下发。
8. 判断配置整体返回结果，等待 OP 并完成握手。任一配置失败均终止本次启动，关闭并重新初始化主站。逐项读回映射可用于后续工程诊断，不作为功能支持性判断的前置步骤。
9. 仅在功能静态审核通过且整体启动成功后，发布该功能的能力状态与句柄；记录所采用的验证证据。

SDK 作者确认普通 SDO 需先执行 `GM_Config_Download_And_Active()`，且 SDK 不提供在线对象元数据查询。因此功能支持性由 ESI 和设备规则在下发前判断，不要求主站做额外字典验证。SDK 作者确认修改 `Slave_info` 中的 PDO 条目可配置从站映射。`GM_PDO_Map_Get()` 的 FPGA 上游来源尚不明确，但不影响本方案。

## 4. 数据与接口模型

### 4.1 ESI 设备描述

保存设备身份、对象及子索引、数据类型、位宽、访问权限、PDO 映射属性、候选 PDO、SM 信息、DC 模式及相关限制。保留文件来源、内容摘要和解析器版本，缓存随来源变化失效。

每条证据还需区分原始 ESI 声明、PDO 推导、解析器补值/修正和未知；未知不能被默认值悄悄替代。单个 `objects_may_be_synthesized` 布尔值不足以供审核。按 PDO 与 SDO 路径分别使用权限证据，不把 SDO Access 简单等同于过程数据能力。现有 schema v1 尚未满足这些要求。

解析器必须保留规划所需的限制信息。只输出对象名称和索引的解析结果不足以直接生成配置。多个 ESI 对同一身份给出冲突描述时应报告冲突。

### 4.2 设备功能定义

描述“应用功能如何由该设备实现”，与 ESI 设备描述关联：

- 功能标识、适用设备及版本、从站级或轴级作用范围。
- 所需的一个或多个对象、子索引、类型、位宽和读写权限。
- PDO / SDO 通信要求、允许的替代实现，以及必要的状态和模式条件。
- 控制值、位掩码、单位或换算规则；共享同一控制字时的写入协调规则。
- 多轴设备各轴的对象映射关系。

对象存在不一定代表整项功能完整。例如某功能同时需要命令和反馈，应在全部依赖满足后启用。

### 4.3 从站实例与能力状态

同型号设备可共享只读描述，每台实例独立保存位置、身份、各轴绑定、能力状态和诊断。

区分物理从站、从站内轴和上层逻辑轴。当前 `HalAxisId` 继续用于轴功能；从站级功能需要独立寻址，避免将整台设备功能重复绑定到每根轴。

能力状态至少能区分：未审核、信息不足、设备不支持、配置未启用、绑定待启动、已就绪、启动失败。已就绪表示静态审核通过且整体启动成功；不声称每项映射都已独立读回。运行中的总线故障与静态能力缺失分别报告。

### 4.4 对外接口

具体命名在 P1 确定，预计需要：

- 枚举从站实例，查询身份和轴关系。
- 查询某个从站 / 轴的功能状态、通信方式和不可用原因。
- 查询启动诊断，失败后仍可读取原因。
- 功能调用增加能力检查；缺失返回明确的“不支持”错误。
- 状态数据增加字段有效性表达，不能用零表示“不支持读取”。

现有公共 C ABI 有严格版本及结构大小检查。新增函数、返回码和布局变更必须按项目规则更新 ABI 版本、导出表、公开头文件和调用方样例。

## 7. 关键测试场景

| 场景 | 预期结果 |
| --- | --- |
| A 有示例报警功能，B 没有 | A 可调用；B 报不支持，其他有效功能继续工作 |
| 对象存在但不能映射 PDO | PDO 功能不可用；只有明确提供 SDO 实现时才允许通过对应非实时接口操作 |
| 一个功能依赖两个对象，仅存在一个 | 整项功能不启用，诊断指出缺失依赖 |
| ESI 不存在、版本不符或描述冲突 | 独立诊断，不自动猜测匹配 |
| ESI 对象信息不完整 | 标记信息不足；必需功能阻止启动，可选功能禁用 |
| 缺少机床所需位置控制功能 | 阻止运行，指出从站和依赖 |
| PDO 配置被拒绝 | 整次启动失败，不发布任何运行功能；报告主站错误及配置计划上下文，关闭并重新初始化主站 |
| 两台同型号从站 | 独立实例和句柄，不互相写入 |
| 一台多轴从站 | 从站级功能和各轴功能作用范围正确 |
| 可选反馈缺失 | 字段标记无效，不用零伪装有效值 |
| 配置中途失败后重新启动 | 清除旧状态，关闭并重新初始化后重新审核与绑定 |
| 无 CoE、只有固定过程数据的设备 | 不套用伺服 CoE 假设，按首批支持范围处理 |
