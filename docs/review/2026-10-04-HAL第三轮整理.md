## 范围

本轮基于 `4487f1c`（首轮修复 + 二次审查已提交）做了一次全量代码与文档审查，
然后按"先建防线、再动代码"的顺序分七批修复。全部改动已提交，工作区干净。

审查覆盖：9 个生产 C 源文件、全部测试与示例、`docs/` 下所有文档，外加厂商 SDK 手册与

## 一、先做的事：把"改坏了也不会红"的地方补上

审查中最值得警惕的不是某个 bug，而是**测试给了假的信心**。用变异测试确认：把下面各处
实现改坏，`1644 + 1810 + 63` 项回归**全部照绿**：

| 变异 | 原后果 |
|---|---|
| `hal_context_start()` 把 `MASTER_START_TIMEOUT` 翻成 `HAL_ERROR_BUS` | 启动超时被报成总线错误（上层警报号会错） |
| `hal_rt_axis_write_pos()` 去掉 CSP 模式闸门 | 位置目标可以下发给速度模式的驱动器 |
| `identity_hash()` 的 FNV 起始值改成 0 | `device_id` 在 serial==0 时恒为同一常量 |
| `family_index` 的两处自增删掉 | "同型号第几台"永远是 0 |
| 字典解析十进制基数改成 8 | `"010"` 解析成 8 而不是 10 |

第 2 批加断言后，**这五个变异全部变红**（每一条都在干净副本上复跑确认）。
补充说明两点，避免把覆盖说大：

- 启动超时那处只补了"驱动层返回 START_TIMEOUT → HAL 返回 TIMEOUT"这一条；
  `hal_context_start` 里"启动总预算已耗尽"那个分支仍未覆盖（`context_regression`
  没有 wrap `clock_gettime`，`elapsed` 不可能超过预算）。
- 位置写入的 CSP 闸门有**两个分句**：`desired_mode != CSP` 与 `mode != CSP`。
  后者在 `motion_ready` 成立时必然相等（`Ds402_Step` 只在模式一致时给 `DONE`），
  属冗余保护。测试覆盖的是前者（主轴处于 CSV 使能态），注释里已写明这一点。

## 二、逐批做了什么

### 第 1 批 · 文档纠错（`692d343`，纯文档与注释）

- **`device.h` 的单位注释写反**：注释说 EEPROM 分类头的 `length` "通常代表字节数"，
  而 `device.c` 是 `header.length * 2`（按 Word）。**代码是对的、注释是错的**，
  而且是全场最容易被后人"照注释改代码"的一处，优先修掉。
- **`api-reference.md` 自相矛盾**：§3.4 用整节文档化了 `hal_io_image_size()`，
  而 §4.4 两处仍写着"当前没有公开的映像长度查询函数"，示例还硬编码 `x_image[64]`。
  这个函数正是 ABI 5.0 为解决该问题而加的。
- `代码导读.html` 的状态机梯子仍是旧值 `OperationEnabled (0x237)`，改为 `0x27`，
  并补注"使能那一拍也会预置目标位置"。
- 交接文档：`CYCLE_TIME` 已不存在（这几项现由 `HalCConfig` 传入）；路径
  `/home/mxh/CNC/HAL` → `cnc_hal`；`sync.sh` 需显式给目录；删掉"`build/all/` 有过期
  `libcnc_hal.so.1.1`"（全新构建目录无此文件）；"绝不能 `git add -A`"标注为仅限
  `cnc_rt`（该仓库有子模块，本仓库没有）。
- 交接文档 §七 中 DS402 两处的 76 行**已作废**历史正文移入附录 A，正文只留结论与上机判据。
- 驱动层 README：接口数 15 → 16（补上漏掉的 `Master_ServoHasRole`）；
  对照副本目录 `DEMO_LIB_AUTO_0920` 已不在本机，改为指向 git 历史。

### 第 2 批 · 补测试（`e4b0b70`）

见第一节。另外：

- 字典 63 例原先只验"收不收"，现在对 `hex` / `decimal_string` / `unicode` / `valid` /

- DS402 穷举从 3 种调用组合扩到 5 种（补 `DROP_VOLTAGE` / `FAULT_RESET`）。

### 第 3 批 · examples 闸门如实化 + 轴号统一（`f54d506`）

**闸门的真实状态**：`hal_hardware_test_config.c` 自 `923e596`（2026-09-24「修改了机床的
默认配置」）起就是**填好的台架配置**（末尾 `return 0`），四个 `confirmed` 标志也是在那个
提交里**以 1 加入**的。所以不是"漏锁"，而是文件注释和 `examples/测试用例用法.md` 仍在描述
"待填模板、未确认就锁死"的旧状态。处理：

- `io_images_confirmed` 由 1 改为 **0**：`y_safe` 当前只有 1 个字节非零、其余全 0，
  而该字段的注释声明是"两幅完整 Y 映像已经逐位核对"，文档自己也写着"全零不等于安全"。
  改 0 后 `io` 用例在 `io_case` 里被拒绝运行。
- 文件内注释不再教"把 `return -1` 改成 `return 0`"；文档增补"当前配置状态"，
  写明哪些已填、哪些仍是占位、哪些必须现场复核。

**轴号统一**（改为与交接文档的 X=0/Y=1/Z=2/主轴=3 一致）：

- 配置：进给轴逻辑号 1..3 → 0..2；主轴 0 → 3。
- `hal_hardware_test.c` 里 **18 处**硬编码的主轴轴号 `0` → `spindle_axis(r)`（从配置读）。
  其中 `hal_rt_axis_set_pos(r->ctx, 0, 0.0)` 走的是通用轴接口、**不经过主轴检查**，
  编号一改会**静默把 X 轴的坐标基准清零**——正是交接文档 §5.5 当初改编号要消灭的那类错误。
- `selftest` 断言、`selftest()` 内部合成配置、用法说明、`config.h` 注释同步。

### 第 4 批 · 驱动层：并发、打断与释放顺序（`a1f91fd`）

- **`InterruptFlag` 改为 `atomic_int`**：它会被 SDK 的错误回调线程写、被本线程的 SDK
  阻塞调用轮询，而原先只有它是普通 `int`——同文件里的注释自己就写着
  "不跨线程写入 SDK 接收的普通 int"。
- **`Master_RequestStop()` 也置打断位**，否则启动期的阻塞调用停不下来。
- **`device.c` 的 `GM_EEPROM_Get` / `GM_PDO_Map_Get` 接上真正的打断标志**并在返回后检查。
  原先传的是函数内的局部 `int = 0`、全流程无人置 1：某台从站不应答要干等满 10 秒，
  30 台从站最坏 300 秒。
- **释放顺序改回厂商示例的顺序**（先 `GM_Free_PDO_Map` 再 `GM_Master_Close`）。
  原先反着来，等于假设 `GM_Master_Close` 不会先动那条链——未经任何验证。
- **`record_warn` 不再在实时周期里调 `PdoWar_Info_Get`**：那是 SDK 的打印型接口
  （`OutFile=NULL` 即打到 stdout），持续告警会变成每拍 `printf` 拖住实时线程。
  详情移到非 RT 的 `Master_BusHealth()`。
- `err_call_back` 的 `Err_info` 先清零再取（失败时 SDK 不保证出参被填）。
- `g_start_error` 在函数入口就清（原先几条提前 return 会把上一次的失败原因当成这一次报出去）。
- IO/面板装配失败补上从站与槽号。

新增 `interrupt_wiring_tests` 验证打断真的接上；"`RequestStop` 不置位"与
"`device.c` 又传局部 int"两处回退变异均已确认变红。

### 第 6 批 · 删除未构建的 C++ 接口层（`a691c8a`）

删除 `src/internal/` 下的 `DeviceBase.cpp/.h`、`IDevice.h`、`HalTypes.h`、`HalError.h`、
`ConfigModel.h`，以及 `src/Dio/IDIO.h`、`test/device_base_test.cpp`
（8 个文件、约 566 行）。理由：

- 不产出任何库、没有公共入口、不被任何编译目标包含——只有 `run_driver_tests.py`
  单独编了一个 `DeviceBase.cpp` 去跑 `device_base_test.cpp`。
- 其中 `IDIO.h`（90 行）与 `ConfigModel.h`（80 行）**从未被任何编译器打开过**：
  `IDIO.h` 没有任何包含者，`ConfigModel.h` 只被 `IDIO.h` 包含。里面有语法错误也没人知道。
- 它还引用了三处不存在的东西：`src/internal/EntryBits.h`、`HalIoMap`、
  `include/c_api/hal_types.h`（实际路径是 `include/hal_types.h`）。
- 留着它，读者会以为那是本工程的架构。C 运行层已覆盖同样职责，并有 1679 项回归。

### 第 7 批 · 收尾小项（`c1d0efc`）

- IO/面板的 X/Y 起始地址加上界 65535。原先只查 `>= 0`，手滑填一个大数会让映像长度涨到
  GB 级，调用方按 `hal_io_image_size()` 的返回值分配就是一次巨型分配。
- `hal_context` 的 `owner` 改为原子指针：`hal_context_request_stop()` 允许与周期调用并发，
  它要读 `owner` 而 start/stop 会写它。
- `slave_list.h` 三个 `create_empty_*` 的 `()` 改成 `(void)`：在 C 里 `()` 表示
  "参数未指定"，传错参数也编得过。
- `devdict.c` 内层的 `keys` 改名 `entry_keys`，消掉与外层的同名遮蔽。
- `entry_access.c` 注明 Entry 句柄有**两个来源**（`DeviceTable` 的快照 vs `g_device_data`），
  改动时必须同时看两处。
- `export.h` 注明 version script 只对**动态库**生效：静态归档里本层的通用符号
  （`err_call_back` / `device_match` / `slave_list` / `g_device_data` 等）会进宿主全局符号空间。

## 四、本轮的边界与未做项

- **未连接任何真实主站或驱动器。** 所有验证都是离线的；每一批的"已修复"都只代表
  离线可验的部分。
- **未修改 `cnc_rt`。** RT 侧持有的仍是 `8844979` 的旧副本；接入前需按
  `sync.sh /home/mxh/CNC/cnc_hal` 重新同步，并重跑 RT 两种构建与离线冒烟。
- **刻意跳过一项**：`find_axis()` 的 const 修正（`-Wcast-qual` 告警）。它要改 12 个
  调用点，而该告警只在扩展警告集下出现（项目构建用 `-Wall -Wextra`，不报）。
- **未动**：`hal_rt_axis_fault_reset()` 要求"begin 与 commit 之间"、而 `enable` /
  `estop` / `request_mode` 在任意相位都可调——这条接口不一致留待下次动公共 ABI 时统一。
- **仍待现场确认**（与本轮无关）：速度 PDO 单位、DC `0x300` 还是 `0x100`、SYNC1 零周期
  语义、`encoder_type` 只校验不消费、拓扑指纹未启用、位置 PDO 对所有轴强制、
  从站掉出 OP（寄存器 0x130）无检测、动态库 SONAME 仍为 3 而公共 ABI 为 5。
