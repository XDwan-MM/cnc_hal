# cnc_rt 接入计划：从基线看还差什么（2026-10-04）

## 这份文档是什么

`cnc_rt` 的目标是**在同事给的稳定版基线上引入本 HAL**。本文从**基线**出发，还原基线
原来是怎么驱动硬件的，再对照当前状态，指出还差哪几步。

本文写在 HAL 仓库里，**不改 `cnc_rt` 的任何代码**。所有结论都带 `文件:行号` 或提交号。

## 二、基线原来是怎么让轴动的

### 2.1 意图：一个贯穿全局的业务标志

```
is_disable = (参数域 PAR_AX_DISABLE) 或 (PLC 的 G124「各轴屏蔽」)
```

- G124 写入：`src/plc/plc_scanner/plc_g_signal_scanner.c:503/508`（上升沿置 `plc_is_disable=1`，下降沿清 0）
- 综合成 `is_disable`：`src/protect/stored_stroke_check.c:234-240`
  （条件为"`PAR_AX_DISABLE` 为 0 且 `plc_is_disable` 为 0"时清 0，否则置 1）
- 基线里 `is_disable` 被 **14 处**业务代码读取：`emcmot.cpp`、`servosamplesampler.cpp`、
  `ferror_control.c`、`plc_f_signal_handler.c`、`global.c`、`master.c` 等

### 2.2 翻译：每拍的 DS402 梯子

PDO 线程每拍调 `Master_Run()`（`src/threads/threads_controller.cpp:179/181`）。
`Master_Run()` 在 `src/master/master.c:117-283`，里面做两件事：

1. **没被屏蔽的轴 → 推 DS402 使能梯子**：写 `0x06`（Shutdown，:169）、`0x07`（Switch On，:174）、
   `0x0f`（Enable Operation，:182）
2. **被屏蔽的轴 → 断电**：

```c
/* 基线 src/master/master.c:260 */
if (rt_data->axis_data[i].status.is_disable)
{
    if (i == 3) 写 g_device_data[2].slave.Control_word = 0x00;
    else        写 g_device_data[i + 3].slave.Control_word = 0x00;
}
```

也就是说：**基线是"周期推进里隐含地自动使能"，除非这根轴被屏蔽。** 业务层不需要显式
"申请使能"——它只表达"别使能这一根"，其余由驱动层自己推。

> 附注：基线的 `driver_set_state_on()` / `driver_set_state_off()` / `driver_set_speed_mode()` /
> `driver_set_pos_mode()`（`src/master/master.h:23-26`）**在基线里就没有调用者**，只有声明。
> 所以使能从来不是通过它们做的。

### 2.3 复位与急停

- 复位：基线 `src/protect/alarm.c:76` 调 `Master_Reset()`（`master.c:284`）
- 急停：`handle_estop_cmd()` 做 `nc_set_resetting(ESTOP_RESET)` 与各模式处理；
  按设计推测其**断电效果经由梯形图抬 G124** 再走上面的 `is_disable → 0x00`。
  **这条尚未证实**，判据只能来自真机的梯形图程序。

## 三、当前状态与基线的对照

| 环节 | 基线 `4222562` | 现在 `1d218cf` |
|---|---|---|
| 意图来源 | `axis_data[i].status.is_disable` | **同一标志仍在写、仍被 8 处读** |
| 翻译成硬件动作 | `master.c:260`：`is_disable` → `0x00`；否则跑使能梯子 | **无** |
| 周期入口 | `Master_Run()` | `rt_hal_pdo_loop()` ✓ |
| 故障复位 | `alarm.c:76` → `Master_Reset()` | `alarm.c:152-155` → `rt_hal_request_fault_reset()` ✓ 已接 |
| 急停 | `handle_estop_cmd()` +（推测）G124 | `rt_hal_request_estop()` **全仓库零调用** |
| 使能 | 隐含在 `Master_Run()` 里 | 适配层**没有使能口子**；零调用 `hal_rt_axis_enable()` |
| vendored HAL | — | 仍是 `8844979`（HAL 现为 `7a9a297`）|

### 3.1 两个直接后果

1. **轴永远不使能**：使能梯子随 `Master_Run()` 一起删除，而 HAL 要求显式
   `hal_rt_axis_enable()`，这一步没人补。
2. **`is_disable=1` 不再断电**：原来那句"写 0x00"也没了。

**一个缺失的翻译，同时解释这两件事。** 语义不需要新发明——基线已经定义好了。

> 为什么这不算"接入时删错了"：HAL 比旧驱动**更严格**（它要求调用方显式表达使能意图，
> 自己不推状态机）。这道翻译是换成 HAL 之后**新出现**的，不是被误删的。

### 3.2 另外三处会掩盖失败的地方

| 位置 | 问题 |
|---|---|
| `src/hal/rt_hal_adapter.c:189-195` | 读之前就 `memset`，读失败时**发布零值**；注释写的是"留着上一拍的值更安全"，与代码相反 |
| `src/hal/rt_hal_adapter.c:235-247` | 在调用**之前**清 dirty 且忽略返回值 → 一次失败的下发把意图**静默吃掉** |
| `src/threads/threads_controller.cpp:188` | `if (rc) alarm_report_hal_error(rc);` 把正常停止（`HAL_ERROR_STOPPED`）报成报警 122 |

### 3.3 台账与运动闸门

`src/hal/rt_hal_config.c:29` 的 `recompute_todo()` **无条件**把 `RT_HAL_TODO_IO_MAP |
RT_HAL_TODO_MOTION` 置起，所以 `motion_allowed()`（`:130`）恒为 0，运动请求一律
`NOT_RUNNING`（`rt_hal_adapter.c:483/493/504`）。这是**有意**的安全闸门，需要的是
"现场确认流程"，不是删除。

## 四、评估

**方向是对的。** 用 HAL 适配层替换旧驱动层、让实时端显式表达意图，正是 HAL 的分工
（HAL 呈现硬件事实，实时端决定是否运动）。20 个提交的顺序也正常，没有跳步；其中
完成屏障带周期号、急停优先且排他、超时停机帧、vendored 依赖、编号对齐这几个判断都站得住。

**但"正确"目前只在结构层面成立**：轴一次都没能真的动起来，离线冒烟跑的是不使能的路径，
所以行为层面从未被验证。加上 3.2 的三处，现在的状态更准确的说法是：
**骨架搭对了，但还看不出它哪里不对。**

## 五、修改计划

按执行顺序排列，每阶段带验收。括号里是依赖。

### P0 · 让 RT 可干活（无依赖）

- 清掉 189 个 `:Zone.Identifier`（Windows 解压残留，让 `git status` 完全没法看）
- 恢复 `lib/cnc_hal/sync.sh` 的可执行位（现在是 `100644`，文档里的 `./sync.sh` 会 permission denied）
- 确认 `git status --porcelain` 只剩 `lib/cncshm/`（子模块位置的普通目录，按交接文档不能 `git add -A`）

**验收**：`git status --porcelain` 只有 1 行。

### P1 · 同步 HAL（依赖 P0）

```bash
cd /home/mxh/CNC/cnc_rt
bash lib/cnc_hal/sync.sh /home/mxh/CNC/cnc_hal   # 用 bash；必须显式给目录
```

然后：重编两种模式 → `test/build_hal_config_check.sh`（45 项）→ 三种离线冒烟。

**验收**：`SYNCED.txt` 记的是 `7a9a297`；冒烟 PASS 且 **FAIL 全 0**；产物哈希与 HAL 侧一致。

**为什么必须在前面**：`HAL-01`（使能前预置位置，防"跳"）与 `HAL-10`（撤销电压不被普通去使能
降级）是安全修复，**现在的 RT 里没有**。不同步，后面每一步都在拿旧 HAL 验证。
注意 `sync.sh` 只记 HEAD、不记 dirty——HAL 现在是干净的，所以这次可信。

### P2 · 恢复 `is_disable` 的翻译（核心，依赖 P1）

在 PDO 线程每拍、`take_requests()` 之前或之内：

```text
每轴 slot：
    if (rt_data->axis_data[slot].status.is_disable) → 请求停（按该轴 estop_action）
    else                                           → 请求使能
```

**放在哪里需要决策**：

- **(a) 推荐**：PDO 线程读 `rt_data`，调适配层新增的 `rt_hal_request_axis_enable(slot, on)`。
  理由：`is_disable` 是**每拍都要看的状态**（不是事件），每拍读一次与基线 `Master_Run()`
  一一对应；且适配层保持只依赖 HAL，不 include `rt_data`。
- (b) 适配层加 `rt_hal_set_axis_intent(slot, disable)`，由产生 `is_disable` 的地方调用。
  更解耦，但要找齐所有写入点（目前两处：G124 与 `PAR_AX_DISABLE`）。

**验收**：模拟后端加用例——`is_disable` 置 1 → 控制字写 `0x00`；清 0 → 使能梯子推进到
`OperationEnabled`。

### P3 · 适配层补使能口子（依赖 P2，与 P2 同批）

照 `rt_hal_request_estop()`（`rt_hal_adapter.c:513`）的模板加
`rt_hal_request_axis_enable` / `rt_hal_request_spindle_enable`。

**策略建议**：**不受台账阻挡**。它表达的是"要不要上力矩并保持原位"，不是"运动到哪"；
HAL-01 已保证上使能前把目标预置为当前位置。这样使能链可以在台账未清时先离线验通，
而运动仍被死死挡住。

**验收**：申请使能 → 轮询 `read_status().enabled` 变 1 → 撤销变 0；台账未清时申请运动
仍返回 `NOT_RUNNING`。

### P4 · 三处正确性修正（依赖 P1；建议早于 P2 完成，便于调试）

见 3.2。三处都各补一个模拟后端用例（现在都没有测试）。

### P5 · 急停路径（依赖 P2；**需要外部判据**）

若基线急停确实经梯形图抬 G124，则 P2 做完急停自动通了。**这条不能靠推测**——
判据只能来自真机梯形图程序（交接文档里"真机梯形图用了哪些 X 字"本来就是未决项）。

若梯形图不抬 G124：在 `handle_estop_cmd()` 里显式 `rt_hal_request_estop(每轴)`。

**验收**：急停输入 → 该轴控制字变 `0x00`（或按 `estop_action` 去使能）。

### P6 · 台账的现场解除流程（依赖 P2/P3）

给 `RT_HAL_TODO_IO_MAP` 与 `RT_HAL_TODO_MOTION` 一个可查、可审、留痕的现场确认入口
（例如 profile 里两个显式开关 + 台账打印）。**不要删掉这两个位。**

**验收**：`rt_hal_config_todo_count()` 能到 0，且运动请求从 `NOT_RUNNING` 变成受理。

> **这一步做完，这台机床才会第一次真的动**，应由现场签字确认。

### P7 · 潜伏项与上机项

- **负当量**：`main.cpp:48` 是 `units_per_count = pm_munit / pm_pulse`，`pm_munit < 0` 时会算出
  负值而被 HAL 拒。本台架四轴为正，属"换机才发作"。修法：传 `fabs(pm_munit)/pm_pulse`，
  方向留在两个 invert（`main.cpp:53-54` 已按符号设好）。
- **同步来源与字典**：`sync.sh` 不带 `devices.json`。真机启动前必须装字典或设
  `CNC_HAL_DEVICES_JSON`，否则 HAL 拒绝启动。
- **只能上机的**：速度 PDO 单位（rpm 还是 0.1 rpm）、DC 用 `0x300` 还是 `0x100`、
  使能瞬间有没有位移、急停的实际效果、IO 点位逐点核对、停机 Y 映像。

**推荐顺序**：`P0 → P1 → P4 → P2 → P3 → P5 → P6 → P7`
（P4 提前是为了"把失败说清楚"，之后 P2/P3 才好调；P5 卡在梯形图判据上）
