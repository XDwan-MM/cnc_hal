CNC HAL × cnc_rt 代码导读

这份文档带你读完全部代码。建议开两个窗口：一边这份，一边编辑器。
顺序是先看全局，再从 HAL 的门口往里走，最后看 RT 怎么用它。 每节末尾有「停下来想一下」，答得上来就可以往下走。

0 · 这是什么

两个工程，一个关系：cnc_rt 是机床的大脑，HAL 是它的手脚。

工程干什么
/home/mxh/CNC/HAL 硬件抽象层。管 EtherCAT 总线、管驱动器（使能、状态、位置、速度）、管 IO 和面板。 编译成一个静态库 libcnc_hal.a
/home/mxh/CNC/cnc_rt 实时端。跑插补、轨迹、补偿、软限位、PLC、报警。它调用 HAL 来操作硬件

先说清边界，不然读代码时会一直纠结"这个该谁做"。

归 HAL归 cnc_rt
EtherCAT 收发、PDO 映射轨迹规划、插补
驱动器使能、DS402 状态机回零策略、软限位
原始计数 ↔ 毫米/度/rpm 的换算螺距补偿、反向间隙
IO 映像的打包与下发PLC 梯形图、坐标系
把硬件故障变成错误码决定要不要报警、要不要停

最容易被忽略的一条：HAL 不做判断。总线健康它只给你原始计数（CRC 错了多少次、超时多少次）， 什么算异常、要不要报警，全归 RT。

还有一个前提要知道：RT 链接的是 HAL 的静态库副本， 放在 cnc_rt/lib/cnc_hal/ 下（和 lib/parser 那几个库一个套路）。

cnc_rt/lib/cnc_hal/
├── include/          公共头 —— RT 业务代码只看这一层
├── internal/         HAL 内部头 —— 只有调试构建的桩会看
├── lib/libcnc_hal.a  静态库
└── sync.sh           HAL 改了之后重跑这个同步

2 · 四个公共头

HAL 的全部对外能力就在这四个文件里。先读它们，别急着进 .c。

include/
├── hal_types.h         配置与状态的数据结构（最重要，先读它）
├── hal_config_api.h    返回码 + 配置校验 + 错误文本
├── hal_control_api.h   生命周期、设备查询
├── hal_rt_api.h        周期接口（实时线程用）
└── hal_c_api.h         上面四个的聚合头，业务代码只 include 这一个

先读 hal_types.h

打开它，你会先看到一段关于版本闸门的说明。这是整个 ABI 的地基：

include/hal_types.h 
#define HAL_C_ABI_MAJOR  5u
#define HAL_C_ABI_MINOR  0u

typedef struct {
    uint16_t abi_major;    /* 必须 == HAL_C_ABI_MAJOR */
    uint16_t abi_minor;    /* 必须 == HAL_C_ABI_MINOR */
    uint16_t struct_size;  /* 必须 == sizeof(HalCConfig)，精确相等 */
    uint16_t reserved;     /* 必须为 0 */
    ...
} HalCConfig;

为什么要三个字段而不是一个版本号？因为它们是三件不同的事：

  • abi_major 管语义——函数增减、返回码含义变了
  • abi_minor 管布局——结构体字段增删改序
  • struct_size 是最后的保险：精确相等而不是"至少"。 只有精确相等才能挡住"在中间插了个字段"这种旧程序看不出来的改动

RT 那边在main.cpp 里按这三个值填，HAL 在 hal_config_validate() 里逐个对。 对不上就直接拒，不会带着错位的结构体往下跑。

配置长什么样

配置是一份扁平的定长数组——启动时传一次，运行中不再变。看一眼总览：

HalCConfig
├── 版本闸门 + 主站参数（cycle_us / 各种 timeout / dc_enable）
├── axes[30]       进给轴：绑哪个从站、当量多少、急停怎么办
├── spindles[4]    主轴：在通用轴属性之上加 max_speed / 速度窗口
├── ios[30]        普通 IO 模块：从站号 + X/Y 起始字节
└── panels[30]     操作面板：同上 + panel_type

两个设计决定值得注意：

① 主轴单独一张表，没塞进 axes[]。因为主轴多出转速侧的东西（转速上限、到位窗口、CSV↔CSP 切换）， 混在一起会让轴表越来越脏。代价是 HAL 内部要同时遍历两张表——所以你会看到 hal_context.c 里的 axis_at() 这种辅助函数。

② 没有"通道"这一维。hal_types.h 里专门写了理由：通道是加工组织 （一条独立的加工执行流，自己的程序、轴组、坐标系），不是硬件属性。删掉实时端业务层， "轴 3 属于通道 2"就没意义了。

再看 hal_rt_api.h

这是实时线程用的接口。它的文件头注释把周期契约说完了，值得逐字读：

/* 周期面 —— 由单个 RT 线程串行调用，一个周期固定三拍：
 *
 *     hal_rt_wait_cycle()  →  hal_rt_begin_cycle()  →  hal_rt_commit_cycle()
 *
 * wait 是唯一的阻塞点。begin 与 commit 之间可以调 write_* / read_*；
 * read_* 读的是本次 begin 采到的快照，begin 之前没有快照。
 * write_* 一律只暂存，到 commit 才真正下发总线——所以同一拍里
 * 先写后读，读不到自己刚写的值。 */

最后那句话是整个设计里最反直觉的一点，值得单独说。

程序员的直觉是：write_pos(10) 然后 read_pos() 应该读到 10。但这里不是。

为什么：因为 write_* 只是把值放进暂存区（a->pos_command 加个 pos_dirty 标志）， read_* 读的是本拍 begin 从总线采回来的快照。两个东西不是一回事。

这么设计是为了让「一拍」有个明确的边界：begin 之后总线的输入定死，commit 的时候输出一次性发出去。 如果允许边写边读，就得处理"发到一半"的状态。

3 · HAL 内部：三个结构体

打开 src/internal/hal_context.c，先看开头三个结构体。看懂它们，整个文件就没有神秘感了。

HalContext —— 一次 HAL 实例的全部运行数据

src/internal/hal_context.c : struct HalContext 
struct HalContext {
    HalCConfig config;          /* create 时拷入，运行期只读 */
    atomic_int stop_requested;  /* 其它线程可写；周期线程前后查它 */
    int running;                /* start 成功后置 1 */
    int phase;                  /* 0 空闲 / 1 已 wait / 2 已 begin —— 卡调用顺序 */
    int sampled;                /* 跑过至少一轮 begin */
    int fault;                  /* 粘性总线错误，一错到底 */
    int axis_count, io_count, slave_count;
    HalCSlaveInfo slaves[HAL_C_MAX_DEV];
    uint32_t x_size, y_size;    /* 输入/输出映像需要多少字节 */
    Axis axes[HAL_C_MAX_DEV];   /* 前 axis_count 个有效（含主轴） */
    Io   ios[HAL_C_MAX_DEV];    /* 前 io_count 个有效 */
};

phase 是理解周期三拍的关键。它就是个状态机：

phase=0  ──wait_cycle()──▶  phase=1  ──begin_cycle()──▶  phase=2  ──commit_cycle()──▶  phase=0
                                              ▲
                                     你的业务代码在这段里跑
                                     （读写轴、读写 IO）

每个函数开头都检查自己该在哪个 phase，不在就返回 HAL_ERROR_STATE。 这就是"调用顺序错了会当场告诉你"的机制。

Axis —— 一根轴

字段看着多，分成五组就好懂了：

分组字段作用
配置副本cfg、spindle_cfg、identity 启动时从 HalCConfig 拷来的
绑定结果slot、spindle、has_speed、has_error 在驱动设备表里的槽号、是不是主轴、有没有速度/故障 PDO
状态机request、desired_mode、mode、motion_ready 要往哪个 DS402 状态推、要什么模式、实际什么模式
暂存的指令pos_command、speed_command、pos_dirty、speed_dirty begin 与 commit 之间写进来的东西，commit 时发出去
反馈与坐标raw_pos、counts、command_offset、feedback_offset 原始计数、展开后的累计计数、两侧坐标基准

raw_pos 和 counts 为什么要两个？

驱动器给的原始位置是 32 位计数，会回绕（走到 2³¹ 附近翻成负数）。counts 是把它 展开成连续的累计值，方法在 sample_axis() 里：

double delta = signed32(raw - a->raw_pos);   /* 本拍比上拍走了多少 */
if (wrap == MODULAR) delta = remainder(delta, period);   /* 模循环取最短差 */
a->counts += delta;
a->raw_pos = raw;

光有 raw_pos，你没法区分"往前走了 10 个计数"和"往后退了 4294967286 个计数"。

Io —— 一块 IO 模块或面板

面板和 IO 模块共用这个结构，差别只在绑定时的类型过滤和 Entry 来源。

Io
├── slot         在驱动设备表里的槽号
├── x, y         这一段映像在 PLC 地址域里的字节基址
├── in_count/out_count   输入/输出 Entry 的个数
├── in_bits[64]/out_bits[64]   每个 Entry 的位长
├── inputs[256]  本拍按位序打包好的输入映像
└── outputs[64]  待下发的输出值，每个 Entry 一个词

为什么要存每个 Entry 的位长？因为不同设备的 Entry 小数位数不一样， 不能假定都是 16 位。bind_io() 会把位长累加起来算出一段占多少字节（(总位数+7)/8）， 采样时还会拿实际读到的位长跟它对一下——对不上直接报 HAL_ERROR_BUS， 不静默错位。

4 · 上电：create 与 start

这两个函数把配置变成能用的东西。分两步是故意的：create 不碰硬件，start 才碰。

1hal_context_create()

src/internal/hal_context.c : hal_context_create()（第 263 行） 
hal_context_create(config, &ctx, err, len)
  ├─ hal_config_validate(config, err, len)   ← 静态校验，不碰设备
  ├─ calloc 分配 HalContext
  ├─ c->config = *config                     ← 拷一份，不持有调用方的指针
  ├─ atomic_init(stop_requested, 0)
  └─ reset_runtime(c)                        ← 清快照、把配置整理成内部 axes[]/ios[]

为什么 create 之后不能直接用？因为这时候还不知道总线上到底挂了什么。 create 成功只说明"配置自洽、内存分配好了"。真正的绑定要等 start。

这也解释了为什么 build_hal_config_check.sh 能离线跑——它只用到 create 之前的静态校验。

2hal_context_start()

src/internal/hal_context.c : hal_context_start()（第 281 行）

按顺序做六件事：

  1. 检查 owner —— SDK 的主站是进程全局单例，已有 context 启动过就拒
  2. reset_runtime() —— 清掉上次运行的残留
  3. 构造 MasterConfig —— 从公共配置翻译成驱动层认识的格式
  4. ethercat_init() —— 启动主站：读 EEPROM、分配 PDO 资源、握手进 OP
  5. DeviceTable_Get() —— 拿到实际扫描出来的设备槽表
  6. 逐轴 bind_axis()、逐 IO bind_io()，最后检查地址段有没有重叠

重点看第 6 步。bind_axis() 干的事是用配置里的（从站号，从站内轴号）去设备表里认领这一轴：

src/internal/hal_context.c : bind_axis()（第 160 行） 
for (int i = 0; i < count; ++i) {
    const DeviceSlot* s = &slots[i];
    if (s->slave_pos != a->cfg.slave_pos || s->axis_index != a->cfg.axis_index) continue;
    if (s->type != SERVO_TYPE && s->type != GREE_AXIS6_TYPE && ...) continue;
    a->slot = i;
    /* 关键：查 PDO 的位长对不对 */
    if (h->statusWord.bit_length != 16 || h->act_pos.bit_length != 32 || ...)
        return HAL_ERROR_UNSUPPORTED;
    a->has_speed = h->act_speed.bit_length == 32 && h->target_speed.bit_length == 32;
    ...

绑不上就不让启动，不做降级。找不到设备、类型不对、PDO 位长不符—— 任何一条都直接失败。理由很简单：一台轴绑不上的机床不能跑， 与其带着半个配置启动、之后在现场某个动作里突然出错，不如启动时就死给你看。

三个编号，别搞混

这是最容易出错的地方，专门说一下：

叫法是什么谁给
逻辑轴号（HalAxisId） HAL 对外的轴标识，业务代码用它寻址 配置里的 logical_axis 字段
槽号（slot） 在驱动设备表里的下标 start 时绑出来的
从站位置 + 轴序号 总线上的物理位置（一台从站可能含多根轴） 配置里指定，用来认领设备

find_axis() 遍历 axes[] 比较 logical_axis == id， 不是直接访问 axes[id]——因为它俩不是一回事。

5 · 一个周期：三拍

这是 HAL 的核心。三拍各自干什么，读 hal_rt_api.h 的头注释就够，这里讲"为什么"。

1hal_rt_wait_cycle() —— 等节拍

src/internal/hal_context.c : hal_rt_wait_cycle()（第 515 行） 
int32_t hal_rt_wait_cycle(HalContext* c) {
    int rc = gate(c); if (rc) return rc;          /* 空指针/未运行/已停止/故障闭锁 */
    if (c->phase != 0) return HAL_ERROR_STATE;    /* 上一拍没走完 */
    rc = Master_WaitCycle();                     /* ★ 唯一的阻塞点：等周期中断 + 收一帧 */
    if (atomic_load(&c->stop_requested) || rc == MASTER_STOP_REQUESTED) return HAL_ERROR_STOPPED;
    if (rc) return bus_error(c);
    c->phase = 1;
    return HAL_OK;
}

Master_WaitCycle() 内部是 SDK 的 GM_Wait_Master_Sync() + GM_Master_Receive()。 等不到就等，等超时就报错。

2hal_rt_begin_cycle() —— 采样 + 推状态机

src/internal/hal_context.c : hal_rt_begin_cycle()（第 575 行）

这一步有意思的地方在于它跑两遍循环：

/* 第一遍：所有轴先采样、算好这一拍状态机要做什么，不写任何 PDO */
for (int i = 0; i < c->axis_count; ++i) {
    Axis* a = &c->axes[i];
    if (sample_axis(a)) return bus_error(c);        /* 读五个 PDO 角色 */
    ...
    planned[i] = Ds402_NextStepReq(a->status.raw_status, ..., a->request, ...);
    ...
}

/* 第二遍：确认全部没问题了，才真的写控制 PDO */
for (int i = 0; i < c->axis_count; ++i) { ... Master_ServoStep(...) ... }

为什么要两遍？因为如果边算边写，第 3 根轴在算的时候发现换算有问题、要返回错误， 前两根轴的控制字已经写出去了。那就成了"部分使能"——比整拍失败更难收拾的状态。

所以：先全部算完，确认无误，再统一写。

sample_axis() 读五样东西：实际位置、状态字、实际模式、故障码、实际速度。 然后做那件重要的事——把原始计数展开成累计计数（见第 3 节的 raw_pos / counts）， 最后按反馈当量和 enc_off 算出用户单位的位置。

3hal_rt_commit_cycle() —— 下发

src/internal/hal_context.c : hal_rt_commit_cycle()（第 647 行） 
/* 先处理急停：它可能在 begin 之后才到达，要覆盖本拍旧的控制字和速度目标 */
if ((a->zero_speed || a->stop_override) && a->has_speed)
    Master_ServoWrite(a->slot, DEV_DICT_ROLE_TARGET_SPEED, 0);
if (a->stop_override)
    Master_ServoWrite(a->slot, DEV_DICT_ROLE_CONTROL_WORD, ...);

/* 再发本拍暂存的指令 */
if (a->pos_dirty)   Master_ServoWrite(a->slot, DEV_DICT_ROLE_TARGET_POS, a->pos_command);
if (a->speed_dirty) Master_ServoWrite(a->slot, DEV_DICT_ROLE_TARGET_SPEED, a->speed_command);

/* IO 同理，整 Entry 下发 */
...

rc = Master_CommitCycle();   /* 最后：GM_Master_Send(1)，整帧发出去 */
c->phase = 0;

急停为什么放在最前面覆盖？因为它是本拍中途才可能到达的。 如果急停发生在 begin 之后，而 begin 已经按"使能"写了控制字， commit 不覆盖的话这一拍照样把使能动作发出去了。

这就是 stop_override 这个字段存在的全部理由。

6 · DS402 状态机

文件：src/common/Ds402.h。它是 header-only、零依赖的纯函数， 可以离线穷举测试——这是有意的，因为它是最不该出错的一段。

驱动器不是"一个使能位"

伺服驱动器上电后不能直接命令它动。它有一套状态机（CiA402 标准），必须一台阶一台阶上：

SwitchOnDisabled (0x40)
      │  写控制字 0x06 (Shutdown)
      ▼
ReadyToSwitchOn (0x21)
      │  写 0x07 (Switch On)  ── 同时必须把目标位置设成当前位置（防飞车）
      ▼
SwitchedOn (0x23)
      │  写 0x0F (Enable Operation)
      ▼
OperationEnabled (0x237)   ← 到这儿才收位置/速度指令

Ds402_NextStepReq() 就是回答"这一拍该写什么"：给它状态字、当前模式、上层请求， 它返回一个 Ds402Step（要写的控制字、要设的模式、要不要预置位置）。

那个"预置目标位置"是防飞车的，不是可选优化。

从 ReadyToSwitchOn 进 SwitchedOn 那一拍，如果目标位置还是 0， 驱动会以为"你要走到零点"，然后全速冲过去。

所以 preset_target 标志为真时，必须先把「目标位置」设成「当前实际位置」。 Ds402.h 里专门写了注释强调这件事。

状态字怎么读

/* 用掩码+期望值的方式判断，对可选位保持宽松——部分固件不置某些位 */
#define DS402_SW_MASK_SWITCH_ON_DISABLED 0x004Fu
#define DS402_SW_VAL_SWITCH_ON_DISABLED  0x0040u
#define DS402_SW_MASK_READY_TO_SWITCH_ON 0x006Fu
#define DS402_SW_VAL_READY_TO_SWITCH_ON  0x0021u
...

判断写法是 (状态字 & MASK) == VAL。不要直接比相等—— 真实驱动器的状态字里有各种可选位（电压有效、快停、远程），直接比会一直判不出来。

还有一条不变量藏在里面：模式不对就不上使能。

在 SwitchedOn 那一级，如果当前模式不是上层要的模式，它会先去改模式 （0x6060），下一拍再上使能。而不是"先使能再说，模式以后再改"。

为什么：让一根轴以错误的模式进入使能态是危险的。

7 · 单位换算

这是全项目最容易出错的地方。文件在 hal_context.c 开头几个小函数，看着不起眼。

只有两条公式

static double feedback_scale(const Axis* a) {
    return a->cfg.feedback_units_per_count * (a->cfg.feedback_invert ? -1 : 1);
}
/* 用户单位 = 计数 × 当量 + 偏移 */
a->status.actual_pos = a->counts * feedback_scale(a) + a->feedback_offset;
static int to_counts(double value, uint32_t* out) {
    if (!isfinite(value)) return HAL_ERROR_ARGUMENT;
    const double rounded = round(value);
    if (rounded < INT32_MIN || rounded > INT32_MAX) return HAL_ERROR_ARGUMENT;  /* 不静默饱和 */
    *out = (uint32_t)(int32_t)rounded;
}

就这些。to_counts() 值得注意的两点：四舍五入，以及 超范围直接拒绝而不是截断——截断会让轴走到一个你没要的位置。

enc_off 的符号是个坑

初始化在 hal_context.c 的 reset_runtime() 里：

/* 兼容 RT 的 enc_off：显示坐标=原始反馈坐标-enc_off；命令反向补回。 */
a->feedback_offset = -a->cfg.enc_off;
a->command_offset  = -a->cfg.enc_off;

注意那个负号。所以配置里传 enc_off 时原样传，不要自己再取反—— HAL 内部已经转了一次。传反了坐标会整体偏 2×enc_off，而且不报错。

模循环展开

主轴这类每转归零的反馈，原始计数是 0..N-1 循环的。展开时不能直接相减：

double delta = signed32(raw - a->raw_pos);
if (a->cfg.feedback_wrap == HAL_WRAP_MODULAR) {
    const double period = a->cfg.feedback_pulses_per_rev;
    delta = remainder(delta, period);   /* 取最短差 */
}
a->counts += delta;

remainder() 而不是 fmod()：前者取绝对值最小的差， 后者保留被除数的符号。从 350° 走到 10°，你要的是 +20° 而不是 -340°。

feedback_pulses_per_rev 填错的话，症状是"主轴跨圈位置跳"。 它必须等于反馈 PDO 的实际每转计数。

上机验证方法：让主轴正好转一整圈，看 position_deg 是否正好变化 360°。

8 · RT 侧：线程拓扑

换到 cnc_rt。先看线程，因为整个 RT 的结构就是"四个线程 + 一堆信号量"。

四个线程

src/threads/threads_controller.cpp 
PDO 线程     rt_hal_pdo_loop()        ◀── 唯一碰 HalContext 的线程
PLC 线程     soft_plc_thread_func()   ── 读写 REG_X / REG_Y
运动线程     motion_controller_thread_func() ── emcmotTrajPlan()
规划线程     path_plan_thread_func()   ── emcmotPathPlan()

实时模式下的调度参数也在同一个文件里：

plc_config    = {.core_id = 3, .policy = SCHED_RR,   .priority = 32};
pdo_config    = {.core_id = 3, .policy = SCHED_FIFO, .priority = 40};
motion_config = {.core_id = 2, .policy = SCHED_FIFO, .priority = 39};
path_plan_config = {.core_id = 2, .policy = SCHED_RR, .priority = 30};

PDO 和 PLC 绑同一个核（3）、运动与规划绑另一个核（2）——靠优先级差保证 PDO 优先。

信号量怎么把它们串起来

src/threads/rt_sem.c 
PDO 线程                           PLC 线程              运动线程
   │                                 │                     │
   │ wait_cycle（等节拍）              │                     │
   │ begin_cycle（采样）               │                     │
   ├─── post plc_sem ────────────────▶│                     │
   ├─── post motion_sem ──────────────┼────────────────────▶│
   │                                 │  干活               │  干活
   │                                 ├── post plc_done_sem │
   │                                 │                     ├── post moton_sem_exec_done
   │◀── 等 plc_done_cycle ────────────┘                     │
   │◀── 等 motion_done_cycle ────────────────────────────────┘
   │ 取走请求 → commit_cycle           │                     │

为什么要"周期号"而不是只等信号量？

信号量的计数只证明"有人 post 过"，不证明 post 的是本拍。 如果运动线程因为某种原因晚了一拍，它的旧结果会被当成下一拍的结果消费掉—— 等于把一拍之前的旧目标当新目标下发。

所以两个业务线程干完活都要写回"我算的是第几拍"，PDO 线程对不上就继续等。 字段就是 plc_done_cycle / motion_done_cycle。

用 __atomic_* 访问，不能裸读——volatile 不是内存屏障。

9 · 适配层

文件：src/hal/rt_hal_adapter.{h,c}。先读头文件顶部那张线程约定表， 整个接入的骨架就在那几行。

为什么要有适配层，不让业务代码直接调 HAL？

因为 HAL 要求"写接口只在 begin 与 commit 之间调用"，而那个窗口只有 PDO 线程在跑。 但业务代码散布在运动线程、PLC 线程、报警路径里。让它们各自去守这个窗口是不现实的。

所以：业务线程只把意图放进请求缓冲，由 PDO 线程统一在本拍取走。

三组口子

读反馈  rt_hal_axis_pos() / _status() / _spindle_speed()
        └─ 读的是 PDO 线程开始前刷新的快照，不碰 context

发命令  rt_hal_request_axis_pos() / _spindle_speed() / _spindle_mode()
        └─ 只写请求缓冲；同拍重复请求后者覆盖前者（不排队）

IO      rt_hal_io_fetch_inputs() / rt_hal_io_publish_outputs()
        └─ PLC 线程取 X 映像、填 Y 映像，真正的总线读写仍在 PDO 线程

周期循环

src/hal/rt_hal_adapter.c : rt_hal_pdo_loop() 
while (!thread_exit_flag) {
    ++cycle;
    rc = hal_rt_wait_cycle(s_ctx);        /* 等节拍、收帧 */
    if (rc) break;
    rc = hal_rt_begin_cycle(s_ctx);       /* 采样、推 DS402、准备输入映像 */
    if (rc) break;
    s_in_cycle = 1;

    publish_snapshot();                   /* 刷新只读快照 */
    s_io_ready = (hal_rt_io_snapshot_inputs(...) == HAL_OK);

    /* 周期号先写再放行——业务线程醒来才知道自己算第几拍 */
    __atomic_store_n(&plc_cycle_target, cycle, __ATOMIC_RELEASE);
    __atomic_store_n(&motion_cycle_target, cycle, __ATOMIC_RELEASE);
    sem_post(&plc_sem); sem_post(&motion_sem); sem_post(&path_plan_sem);

    struct timespec deadline; make_deadline(&deadline);    /* PLC 与运动共用 */
    rc = wait_done("PLC", &plc_done_cycle, &plc_done_sem, cycle, &deadline);
    if (rc) { stop_frame(); break; }
    rc = wait_done("运动", &motion_done_cycle, &moton_sem_exec_done, cycle, &deadline);
    if (rc) { stop_frame(); break; }

    take_requests();                      /* 取走本拍命令并下发 */
    hal_rt_io_flush_outputs(...);
    rc = hal_rt_commit_cycle(s_ctx);      /* 本拍唯一发送出口 */
    s_in_cycle = 0;
    if (rc) break;
}

出错时的 stop_frame() 干三件事：取消所有轴的本拍运动、按停机映像下发输出、提交一帧， 然后退出循环交给调用方走停机流程。

停机映像当前未配置，所以停机帧不写 Y。 不能假设"全零就是安全状态"——必须按实际接线逐位确定，由 rt_hal_io_set_stop_image() 装上。

10 · 配置从哪来

两条线，分别对应两类配置。

线一：硬件拓扑 → 写死在 profile 里

src/hal/rt_hal_config.c 
static const RtHalBinding kBindings[RT_HAL_AXIS_COUNT] = {
    {"X",  RT_SLAVE_X,       0, 0, 0},   /* RT 槽 0 → 从站 3，HAL 逻辑轴号 0 */
    {"Y",  RT_SLAVE_Y,       0, 1, 0},
    {"Z",  RT_SLAVE_Z,       0, 2, 0},
    {"SP", RT_SLAVE_SPINDLE, 0, 3, 1},   /* 主轴在从站 2 */
};

这些是机床装配事实——哪根轴插在总线的哪个位置。改拓扑要改代码。

线二：换算量 → 从机床参数域取

当量、enc_off 这些每台机床不同，存在共享内存的参数域里 （Qt 界面写进去的）。RT 启动时读出来：

main.cpp : fill_hal_params() 
const RT_AXIS* a = &rt_data->axis_data[rt_slot[i]];
if (a->pm_pulse == 0 || a->pm_munit == 0) continue;   /* 参数缺失 → 不装载 */

params[i].scaling.units_per_count = (double)a->pm_munit / (double)a->pm_pulse;
params[i].scaling.enc_off         = a->enc_off;        /* 原样，不取反 */
params[i].scaling.feedback_pulses_per_rev = a->mt_ppr > 0 ? a->mt_ppr : a->pm_pulse;

未确认台账：一个"挡住运动"的开关

如果换算依据没确认，宁可挡住运动，也不猜一个值让程序继续。 实现是一个位掩码：

src/hal/rt_hal_config.c : recompute_todo() 
uint32_t t = RT_HAL_TODO_IO_MAP | RT_HAL_TODO_MOTION;   /* 两个常量位，只能改代码清 */
for (int i = 0; i < RT_HAL_AXIS_COUNT; ++i) {
    if (!s_scaling_ok[i]) t |= RT_HAL_TODO_SCALING | RT_HAL_TODO_ENC_OFF;
    if (!s_pulses_ok[i])  t |= RT_HAL_TODO_ENCODER;
}
s_todo = t;

任何要动的地方都得先过 rt_hal_config_motion_allowed()。 启动日志里会把没清的项逐条打出来。

注意"开放运动"是改代码，不是改配置。 IO_MAP 和 MOTION 是写死的常量位，只能删掉才清。 这是有意设计的闸门——它要的是一次"我确认过了"的显式动作。

11 · 一根轴动起来

现在把前面全串起来，跟着一次位置指令走完。

读取反馈

if (rt_hal_axis_pos(RT_HAL_AXIS_X, &pos) == HAL_OK)

主轴是特例

主轴的转速走另一条路。spl_control.c 里有个软件斜坡—— RT 自己算加减速，每个周期把当前该有的转速发给 HAL：

const double spd = spl_data.current_speed;
(void)rt_hal_request_spindle_speed(RT_HAL_AXIS_SP, fabs(spd),
                                   spd > 0.0 ? 1 : (spd < 0.0 ? -1 : 0));

注意它把带符号的 rpm 拆成了"幅值 + 方向"——因为 HAL 的接口就是这么设计的 （rpm 必须非负，转向由 dir 给）。

还有个小东西值得知道：spl_ramp_active。

旧代码用 spindle.mode 这个字段同时表达两件事： "RT 要不要继续推进斜坡"和"期望驱动器工作在哪个模式"。

接 HAL 后必须拆开——HAL 里没有"模式关闭"这个状态（只有 CSV/CSP 加使能位）， 而旧的那个语义既不是切模式也不是去使能，纯粹是 RT 自己停推斜坡。 所以它是 RT 本地的一个变量，就是 spl_ramp_active。

12 · 故障与复位

文件：src/protect/alarm.c。

两类错误要分清

类别来源怎么处理
总线错误HAL 的周期调用返回非零 HAL 内部闭锁——首个错误码被记住，此后每个周期调用都返回它，直到 stop/start
驱动器故障状态字的 Fault 位（0x0008） 要发"故障复位"清除，清完轴停在未使能

HAL 错误 → 报警号

src/protect/alarm.c 
#define HAL_ALARM_BUS            120  /* 总线错误 */
#define HAL_ALARM_TIMEOUT        121
#define HAL_ALARM_NOT_RUNNING    123
...
#define HAL_ALARM_RESET_TIMEOUT  131

void alarm_report_hal_error(int32_t rc) {
    if (rc == HAL_OK) return;
    char text[96];
    hal_error_text(rc, text, sizeof(text));      /* HAL 给中文描述 */
    setAlarm(ALARM_ETHCAT_SV, ALARM_ERROR, hal_code_to_alarm(rc));
}

HAL 的错误码是正数，不能沿用旧 RT 那套 rc < 0 判断。 这是接入时最容易写错的一处——写错了会"出错当成功"，而且不报错。

为什么是 PDO 线程来报错

有一段曲折值得知道。alarm_poll_hal() 本来放在运动线程里每拍调， 但周期循环一旦因总线错误退出，PDO 线程就不再 post motion_sem， 运动线程会卡在 sem_wait 上——alarm_poll_hal 再也不会跑。

报警恰好会在最该报的时候丢掉。

所以现在的做法是：发现错误的人（PDO 线程）自己报。 pdo_thread_func 拿到 rt_hal_pdo_loop() 的返回值后直接调 alarm_report_hal_error()。

故障复位链

操作员按复位（或急停 G8.4 由 0 变 1 触发自动复位）
   │
   ▼  task_handle_hmi_event → rt_data->nc_event = SYS_EVENT_HMI_RESET
   │
   ▼  handle_alarm_cmd()：清报警、重置数据
   │     └─ rt_hal_request_fault_reset() × 4 轴   ← 只记意图
   │
   ▼  PDO 线程 take_requests()
hal_rt_axis_fault_reset(ctx, id)
   │     └─ 置 request = DS402_REQ_FAULT_RESET，记下超时周期号
   │
   ▼  下一拍 begin_cycle()：状态字还有 Fault 位就写控制字 0x80
   │     （每拍重发，直到离开 Fault 或超时）
   │
   ▼  状态字离开 Fault → reset_state = DONE，request 改回 DISABLE
   │
   ▼  alarm_poll_hal()：四轴都到终态 → 记录"复位完成，轴保持未使能"

复位后是未使能，不会自动恢复运动。 要继续动必须显式重新使能，并再经一次 begin 确认状态机到位。

这是有意的：驱动器刚从故障恢复时自动上使能是危险的。
