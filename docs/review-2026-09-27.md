当前两条路径是：

```text
运行路径：机床配置 → ethercat_init → EEPROM/回退扫描及构造 Slave_info
        → 可选快照 → 计算布局/取句柄 → 下发 → OP/握手
        → HAL 按机床用途绑定和检查 → 发布运行状态

离线路径：ESI → KickCAT → JSON 索引
        + 拓扑快照 + devices.json → Python 审核报告
```

离线报告没有进入运行路径；JSON 报告中的通过或阻断不会改变实际主站行为。

## 2. 优先解决的发现

### A. 审核输入还不能直接作为配置授权依据

- `third_party/kickcat_esi/lib/src/ESI/Parser.cc` 的 `synthesizePdoTargetObjects()` 会从 PDO 补出对象、类型和访问位；`loadAccess()` 对缺少 Flags 的对象补默认读权限。还存在替换映射/分配对象和修正映射子索引的路径。这些是本地所引入版本的行为，不能把输出整体视为 ESI 原始声明。
- `tools/esi_extract.cpp` 仅给出设备级 `objects_may_be_synthesized=true`，没有逐对象/字段来源；审核器未检查这个标记。
- 提取结果省略部分约束，例如 DC 周期/偏移、InitCmd、部分 PDO/SM 属性；缺省值与未声明也未完全区分。成功解析不代表足够生成配置。
- ESI 未列出对象可能代表描述不全。当前 `object_missing` 可阻断必需角色，但不能据此宣布设备一定不支持；“证据不足”和“明确不支持”必须保留区别。
- PDO 声明是过程数据证据，SDO Access 是访问证据；不能把二者简单等同。需按具体通信路径审核，也不能用合成的 Access 推断可进行新的 SDO 写入或动态重映射。

下一步首先保留原始声明、推导值、缺省/未知、解析警告及完整性。允许使用 PDO 声明作为相应过程数据证据，但禁止把推导信息升级成未经声明的权限。

### B. 离线判定与运行实现已经出现差异

复核通过最小输入在内存中重现，未修改项目代码：

| 输入变化 | 当前离线结果 | 问题与预期 |
| --- | --- | --- |
| 主轴有实际速度但缺 `0x60FF` 目标速度映射 | `static_eligible` | `bind_axis()` 要求目标与实际速度均存在；离线依赖漏项 |
| 实际位置对象的类型改成 REAL32，位宽仍为 32 | `static_eligible` | 当前只比较位宽，未比较类型；数值解释会不一致 |
| 重复同一个启用 PDO 条目 | `static_eligible` | Python 用集合消除重复；C `find_object()` 拒绝同方向重复角色 |
| 标记 `objects_may_be_synthesized=true` | `static_eligible` | 标记未参与判定，来源不足不能可靠分级 |
| 删除 ESI 中一个必需对象，但保留映射快照 | `blocked/object_missing` | 阻止授权可以保守处理，但原因应表达 ESI 证据缺失，不能证明从站无对象 |

另有规则语法差异：C 字典支持行内/块注释、缺省 revision 通配和 `target_torque` 等角色；Python 只去掉整行注释、假设 revision 存在，角色表也不完全相同。应统一模型或增加两端一致性测试，不能继续手工维护两套独立规则。

### C. 上一次“直接把审核结果接入启动”的顺序需要修订

- `hal_context_start()` 在 `ethercat_init()` 返回后才执行 `bind_axis()`、IO 绑定与地址范围检查。此时下发、OP、握手已完成。因此“主轴缺依赖会阻止启动成功”不等于“在下发前阻止配置”。
- Python 用 `active_pdo_entries` 才能得出 `static_eligible`，下发前方案永久保持 pending。它作为诊断原型可以成立，但不适合直接作为下发门槛：会形成先启用才能审核、先审核才能启用的循环。
- 约定保持不变：ESI/设备规则审核对象与计划；SDK 执行配置；整体下发成功、OP、握手后发布能力。独立逐项读回只用于可用时的工程诊断，不引入新的主站在线字典验证要求。

应明确两个结果：**静态方案可下发**与**运行功能已就绪**。前者不依赖已启用 PDO 快照；后者依赖本次启动整体结果且与本次计划绑定。

### D. 现有映射和快照不足以承担通用规划

- `device.c` 仍将机型分类、EEPROM 解析、回退取映射和 `Slave_info` 构造合在一起；本地 PDO 解析按 SM2/SM3 筛选，容量为每方向 10 个 PDO、每 PDO 20 条目，多轴仍硬编码。
- EEPROM PDO 标志、完整 SM 信息、默认/强制约束和来源没有完整进入快照。快照仅保留身份、方向、PDO 索引及扁平条目，不是可直接复用的完整配置计划。
- `sync_assign_activate=0x300`、从站 sync0 为固定值；主站周期另取 `cfg->cycle_us`。SDK 是否覆盖这些字段尚未确认，当前不能称为逐设备 DC 配置。
- `CNC_HAL_TOPOLOGY_SNAPSHOT` 仅在完整扫描成功后输出，写入失败只打印错误；同次启动仍继续下发。它不是“只扫描并退出”模式，也没有采集批次/SDK版本/内容摘要。不能用旧文件替代本次扫描来授权启动。

### E. 工程交付边界

- Catalog 有源文件 SHA-256，但未记录解析器/适配器版本、结构化警告和完整性。查询不验证源文件是否更新；冲突比较也只覆盖已提取字段。暂不称为完整缓存失效机制或完整 ESI 冲突检测。
- 历史厂商样本仅在临时目录验证，仓库测试没有固定这些原文件及摘要；3 个文件/10 个设备版本是解析冒烟记录，不是三家设备已适配证明。后续固定可重现的来源清单和脱敏最小样例，并核对分发许可。
- 当前独立工具通过 shell 构建，未纳入 CMake 安装；主回归运行 Python 拓扑审核，但不构建并验证 ESI 提取器。安装产物和真实 SDK 链接仍须另验。
- 公共能力只有 READY/UNSUPPORTED/NOT_CONFIGURED 的初步表达；启动失败后实例信息会被清理。需要独立保存本次诊断，区分缺描述、缺映射和通信故障。扩展公共接口时按 ABI 规则执行。
