## 五、必须知道的设计决定

### 1. 线程契约：context 只有 PDO 线程碰

| 线程 | 允许做什么 |
|---|---|
| 主线程 | `rt_hal_create` / `rt_hal_start` / `rt_hal_shutdown` |
| **PDO 线程** | `rt_hal_pdo_loop()` —— **`HalContext` 的唯一周期访问者** |
| 其他线程 | 只能走三组口子：读反馈快照 / 发命令请求 / IO 两个口子 |

发命令走"请求"而不是直接调 HAL，是因为 HAL 要求写接口只在 `begin` 与 `commit`
之间调用，而那个窗口只有 PDO 线程在跑。

### 2. 完成屏障必须带周期号

PLC 与运动线程干完活都写回"自己算的是第几拍"。**只看信号量计数不够** ——
它只证明"有人 post 过"，不证明 post 的是本拍；迟到的第 N 拍结果会被当成
第 N+1 拍的结果，等于把一拍之前的旧目标当新目标下发。

### 3. 静态链接，旧路径必须同批摘掉

HAL 静态库与 `libethercat.so` 有 **31 个重名符号**（`ethercat_init` 签名不同、
`g_device_data` 布局不同）。实测：HAL 在前 → **段错误（139）**；libethercat 在前 →
HAL 内部调用绑到旧版。**两种顺序都坏**，所以不能共存。

副产品：HAL 的内部符号（39 个非 `hal_` 前缀）会进 RT 的全局符号空间。
动态库有 version script 挡着，静态库没有。现在没有冲突，但将来 RT 自己或别的
静态库定义同名符号会**静默冲突**。

### 4. 未确认台账是**手工闸门**

`recompute_todo()` 里 `IO_MAP` 与 `MOTION` 是**常量位，只能改代码清**。
即使参数全齐也不会自动放开运动。**"开放运动"本质是一次代码修改 + 评审**，
建议做成显式的、带注释的提交。

### 5. 参数映射：HAL 已内建 RT 的 enc_off 语义

代入验证过，两边公式完全等价：

```
HAL: actual_pos = counts × 当量 + feedback_offset   （内部 feedback_offset = −enc_off）
RT : mcs        = pulses × 当量 − enc_off
```

所以 `enc_off` **原样传，不要取反**。当量 = `pm_munit / pm_pulse`。

**索引**：RT 轴索引（`par_axis` / `axis_data[]`）与 HAL 的 `HalAxisId`
**取值刻意相同**：X=0、Y=1、Z=2、主轴=3。

> 2026-09-30 改的。原先是 HAL 用 `ID = 从站号 − 2`（主轴 0、X=1、Y=2、Z=3），
> 与 RT 反着。HAL 对逻辑轴号取值没有要求，选什么本来自由——那就没有理由留一套
> 反着的编号：多一套编号就多一类静默错误（`hal_rt_axis_read_pos(ctx, 0, ...)`
> 看着像 X、实际是主轴，不报错只是轴错了）。

**但 HAL 的配置数组仍然分成两张表**，这一点没变、也别混：

| HAL `HalCConfig` | 装什么 | RT 侧怎么对应 |
|---|---|---|
| `axes[0..2]` | 三根进给 | `fill_axis()` 按 `kBindings[0..2]` 填 |
| `spindles[0]` | 主轴（单独一张表） | `kBindings[3]`（`is_spindle=1`） |

跨到 HAL 的编号仍**只走** `rt_hal_config_hal_axis()` 一个入口，别在调用点自己写数字。

## 六、已知的坑（都是实测踩出来的）

| 坑 | 说明 |
|---|---|
| **`g_device_data` 必须在桩里接管** | 否则链接静态库会连锁拉进整个真驱动层：`hal_context` → `device_identity_get` → `device.c.o` → 需要 `g_device_data` → `main_demo.c.o` → 连环冲突。**用桩替换静态库某一层时，要覆盖的符号集不只取决于"谁引用了它们"，还取决于归档内部的传递引用。** |
| **RT 构建没有 `-Werror`** | 只看 `error:` 会漏掉 `warning: implicit declaration` 那类 —— 实测 `getenv` 漏了 `<stdlib.h>` 导致指针被截断，编过了但功能是坏的。 |
| **构建通过 ≠ 测试覆盖** | `-Wl,--gc-sections` 会把没人调用的新函数连同它的未定义引用一起丢掉。为 ABI 4.0 加接口后 `build_all.sh` 全绿，跑 `ctest` 才暴露 4/4 全败。 |
| **仿真里急停默认是"按下"** | 面板输入全零 = 急停按下（X8.4 低有效），所有复位事件会被拒。而且**真正生效的是 G8.4**（X 那条路 `plc_x_signal_scan_cycle` 压根没被调用）。 |
| **验收脚本要区分 FAIL 与 N/A** | 默认/busfail 模式里有"预期内"的断言不适用，报成 FAIL 会训练人忽略 FAIL，比不报还糟。 |
| **动态库 SONAME 与 ABI 脱节** | 产物名是 `libcnc_hal.so.3.0`（SONAME `libcnc_hal.so.3`），而公共 ABI 是 5.0。走静态库不受影响；一旦切回动态链接，链接器会把 ABI 5 当成 soname 3。 |
| **`lib/cncshm/` 未纳入版本控制** | 这是 **`cnc_rt`** 的坑：它是 `.gitmodules` 声明的子模块，本地是解压出来的普通目录，**提交时只能逐个文件 `git add`，绝不能 `git add -A`**。HAL 仓库（`cnc_hal`）没有子模块，`git add -A` 是安全的。 |

## 七、没做完的 / 卡在哪

### 卡在外部输入

| 项 | 缺什么 | 缺了会怎样 |
|---|---|---|
| **速度 PDO 单位确证** | 查驱动器对象字典 0x606C/0x60FF 的单位，或外部测速 | HAL 已按 **rpm 1:1** 处理；若实际是 0.1 rpm，转速差 10 倍 |
| **运动范围批准** | 现场 | `RT_HAL_TODO_MOTION` 手工门挡住运动 |
| **真机梯形图用了哪些 X 字** | 真机的梯形图程序 | RT 写 X 映像的范围可能覆盖梯形图当线圈用的字节（见下） |

### IO 映像覆盖 vs 梯形图 X 线圈（未决）

`plctask.cpp` 会写 `regX` —— 对 `REG_X` 做按位 SET/RESET（线圈），索引来自运行时
加载的梯形图。而 `_regData(*getRegDataPtr())` 是**共享内存寄存器块的引用、不是副本**，
所以那些线圈直接落在共享内存的 X 区。

PLC 线程每拍把输入映像写进 `X0..X25`，**正好会清掉梯形图在同一段里当线圈用的字节**。
症状是梯形图的边沿检测反复触发（实测：离线跑比基线多出 27 次外部减速 `_ON` 事件）。

**release 路径不受本次改动影响** —— 旧代码也每拍写同一段、同样的内容，行为一致。
但若真机梯形图也在 `X0..X25` 内用线圈，**release 路径一直存在同样的覆盖**，
只是现场未必表现为这个症状。判据只能来自真机的梯形图程序。

相关：**当前真正生效的急停信号是 G8.4**（`plc_g_signal_scanner`），
`X8.4` 那条路（`plc_x_signal_scan_cycle`）在运动线程里是注释掉的、没被调用。

### 位置 PDO 对所有轴强制（已知的过度约束，待触发条件）

**现象**：`bind_axis()` 把 `act_pos`（32 位）与 `target_pos`（32 位）列为**必填**，
对每一根轴都强制，包括纯 CSV 的主轴。缺任意一个 → 返回 `HAL_ERROR_UNSUPPORTED`
→ `hal_context_start()` **整体失败、整台机床起不来**（不是"这一根轴不可用"）。

**这是过度约束**，理由：

- 纯速度模式的主轴只发转速、只读转速，**不需要位置对象**；
- `sample_axis()` 无条件读 `ACTUAL_POS`、DS402 进 `SwitchedOn` 时预置 `TARGET_POS`，
  这两处对 CSV 都是多余的（速度模式驱动根本不看 `0x607A`）；
- 佐证不对称：`hal_axis_capability()` 里 `HAL_FUNC_SPEED` 与 `HAL_FUNC_ERROR_CODE`
  都会诚实报 `HAL_CAP_UNSUPPORTED`，**而 `HAL_FUNC_POSITION` 那一支压根没有**，
  无条件报 `HAL_CAP_READY`。之所以没暴露，是因为位置缺失时 start 早就失败了。

**为什么现在不改**：本台架四台 GreeMaster 伺服都映射了位置对象，**造不出验收场景**。
而这段改动落在周期路径的骨架上（`bind_axis` / `sample_axis` / `begin_cycle` 的
`preset_target` / 能力查询 / 三个位置读写接口），改了没法验等于埋雷。

**触发条件**：出现"只映射速度对象"的驱动器（例如某些变频主轴板卡）。
那时要做的事：

1. `bind_axis()` 加 `has_pos`，位置不再强制
2. `sample_axis()` 条件读 `ACTUAL_POS`，`counts`/`actual_pos` 语义变为"可能无效"
3. `begin_cycle()` 按 `has_pos` 屏蔽 `preset_target`，否则 `Master_ServoStep` 会返 -1、整拍失败
4. `hal_axis_capability()` 的 `HAL_FUNC_POSITION` 分支补上检查
5. `hal_rt_axis_read_pos/write_pos/set_pos` 返回未就绪
6. `HalCAxisStatus.position_valid` 正好用得上（它当前恒为 1，注释里已留了话）

**离线验证方式**：在模拟后端里造一个"不映射位置对象"的槽，即可验完整条路径。

**顺带可单独做的小改进**：绑定失败时的报错文本是
`从站 X 轴 Y 缺少{主轴速度|DS402 控制}必需 PDO 功能` —— **不说是哪个角色缺**，
位置缺和状态字缺给的是同一句。改成逐角色报（"缺少实际位置 PDO"）是几行的事，
不改任何行为。

### DS402 两处待上机确认（上机时优先看这两条）

> 2026-10-04：这两处**均已修复并完成离线回归**。原始分析移到文末「附录 A」，
> 只用于追溯当时的判断，**不要再按其中的旧代码或「为什么现在不改」理解当前实现**。

**① 状态字掩码**：现实现按 `(raw_status & 0x006F) == 0x0027` 判定，bit4/bit9 不参与编码，
bit5 仍用于区分 QuickStopActive。
上机判据：让驱动器走到使能态，读 `hal_rt_axis_read_status().raw_status`，记录实际状态字。

**② 使能瞬间的位移**：`DS402_STEP_ENABLE_OP` 那一拍现在**也会**预置目标位置。
上机判据：急停 → 手动把轴推离原位 → 恢复使能，观察轴是否朝急停前的目标移动。

### 有意保留的

- **停机输出映像未配置** —— 停机帧**不写 Y**。计划书 §8 明确"不能假设全零就是安全状态"，
  与其发一个不知道对不对的映像，不如不发。要配上由 `rt_hal_io_set_stop_image()` 负责。
- **`encoder_type` 是"意图声明"** —— HAL **只校验不消费**这个字段（全仓库无功能性使用点）。
  当前四轴都配成绝对式；但交接记录写的是"主轴为带 Z 相的增量式"，两边迟早要对齐。
- **总线健康计数器没接进报警** —— `hal_bus_health()` 有接口，**RT 侧一处没调**，阈值策略未定。
- **报警体系只覆盖了 HAL 错误码** —— 旧 `ALARM_ETHCAT_SV` 那 52 个调用点随
  `master.c`（267 行错误码查表）一起退休，新映射只把 HAL 的正错误码翻成 120~131；
  PDO 警告、CRC、帧超时那一类没有等价重建。
- **拓扑指纹算法未定** —— `topology_fingerprint` 必须填 0，非零会被拒。

## 八、配置项的归属（哪些该由 Qt 配）

对照参数域查过，分四类：

**① 已经是从参数域取的**（不是暂时的）
- 命令/反馈当量 ← `PAR_AX_PM_MUNIT` / `PAR_AX_PM_PULSE`
- 坐标偏置 ← `PAR_AX_ENC_OFF`
- 每转反馈计数 ← `PAR_AX_MT_PPR`（**优先**，为 0 时退回 `pm_pulse`）

**② 参数域有槽位、但 RT 从没装过**（要用得加装载代码，不动 cncshm）
- `PAR_SPDL_SPD_TOL`（主轴转速允许转速波动率）→ 可作速度窗口，**但单位不明**（0.05 还是 5？）
- `PAR_CH_SPDL0`~`SPDL3`（主轴编号）
- `PAR_AX_PM2_*` / `PAR_AX_ENC2_*`（**第 2 编码器**的当量与偏置）—— HAL 把命令/反馈
  当量分开配本来就是为外接光栅尺准备的，这条将来是通的
- `PAR_AX_ENC_MODE` —— 注意它是**"用第几个编码器"**（位域：用第1/第2/无反馈），
  **不是**增量/绝对，跟 HAL 的 `encoder_type` 不是一回事

**③ 参数域里"有枚举但没有存储"**
- 整张 `PAR_DEV_*` 设备表（60 项）—— 含从站序号、逻辑轴号、IO 起址、面板类型等，
  几乎覆盖了现在硬编码的全部。**但 `ParProp` 里没有装它的数组，全仓库零引用** ——
  是从 HNC-8 参数体系继承来、本系统没接线的定义。要用得先加数组（动 cncshm）。

**④ 参数域里确实没有，也不该有**
- **急停动作**（去使能/撤销电压）—— 参数域无此概念
- **IO/面板 X/Y 地址** —— 决定梯形图的地址语义，跟梯形图程序绑死，不是用户可调参数
- **主站周期/启动预算/周期超时/DC** —— 参数域只有 `PAR_NCU_CYCLE`（插补周期，单位是**秒**），
  与 HAL 无关。2026-10-04 起这几项由实时端填进 `HalCConfig`（`cycle_us` / `start_timeout_ms` /
  `cycle_timeout_ms` / `dc_enable`）传给 HAL，**不再是编译期常量**；旧的 `CYCLE_TIME` 宏已删除

## 九、边界与原则（别越界）

- **HAL 建立并呈现硬件事实，实时端决定机床是否运动。**
  DS402 使能、PDO 交换、设备绑定、原始计数与用户单位换算归 HAL；
  回零策略、软限位、轨迹、跟随误差、坐标系、急停**触发**归实时端。
- **HAL 不创建周期线程**，周期线程由调用方负责。
- **报警策略归上层** —— HAL 的 `hal_bus_health()` 只给原始计数，不做判断。
- **通道（channel）不在 HAL 配置里** —— 通道是加工组织，不是硬件属性。

### DS402 两处待上机确认（**上机时优先看这两条**）

**以下保留 2026-09-30 的审查历史。2026-10-04 两处均已修复并完成离线回归；
当前行为见审查记录，不再以本节的旧代码或“为什么现在不改”作为实现依据。**
使能瞬间的实际位移仍须上机验证，状态字解码规则可以离线核查。

#### ① 状态字掩码比注释严 —— 可能导致"驱动器使能了但 HAL 说没使能"

注释写的是：

```c
/* 状态字 0x6041 的判定掩码。
 * 对可选位（bit4 电压有效 / bit5 快停 / bit9 远程）保持宽松——部分固件不置这些位。 */
#define DS402_SW_MASK_OP_ENABLED         0x027Fu
#define DS402_SW_VAL_OP_ENABLED          0x0237u
```

但把掩码拆开看，它**恰恰要求那三位必须为 1**：

```
0x027F 覆盖 bit[0,1,2,3,4,5,6,9]
0x0237 要求 bit[0,1,2,4,5,9] = 1，bit[3,6] = 0
                      ↑ bit4 电压有效、bit5 快停、bit9 远程
```

**注释描述的是一个没有实现的意图。**

后果：若某台驱动器固件不置 bit4 或 bit9，HAL 会**永远认为它没使能** →
`motion_ready` 永假 → `write_pos` 一直返回 `NOT_RUNNING` → 轴动不了。
现场症状是「驱动器面板/调试软件显示已使能，HAL 说没使能」。

这套掩码是从旧 `master.c` 原样搬的（基线 `4222562` 里就是 `0x4f/0x40`、`0x6f/0x21`、
`0x6f/0x23`、`0x27f/0x237`），所以旧 RT 同一行为。

**上机判据**：让驱动器走到使能态，读 `hal_rt_axis_read_status().raw_status`，
记录驱动器的实际状态字。现实现按 `(raw_status & 0x006F) == 0x0027` 判定，
bit4/bit9 不参与；`0x023F` 带 Fault 位 bit3，不能作为合法使能状态。

#### ② `SwitchedOn → OperationEnabled` 不预置目标位置

`Ds402_NextStepReq` 只在两处置 `preset_target`：进 `SwitchedOn` 那一拍、
以及切模式那一拍。**从 `SwitchedOn` 直接使能时（模式已经对）不预置**：

```c
else if ((status_word & DS402_SW_MASK_SWITCHED_ON) == DS402_SW_VAL_SWITCHED_ON) {
    if (current_mode != desired_op_mode) {
        s.kind = DS402_STEP_SWITCH_MODE;
        s.preset_target = 1;              /* 切模式时预置 */
    } else {
        s.kind = DS402_STEP_ENABLE_OP;    /* ← 直接使能，不预置 */
        s.control_word = DS402_CW_ENABLE_OP;
    }
}
```

**两条常见路径会走到这里**（都不预置）：

1. **急停后恢复**：`estop_action = HAL_ESTOP_DISABLE_OPERATION`（已定）→ `DS402_REQ_DISABLE`
   → 驱动器退回 `SwitchedOn`，**退回时不写 `target_pos`**，里面留着急停前最后一个目标
2. **正常去使能再使能**：`hal_rt_axis_enable(c, id, 0)` 再 `(1)`

后果：驱动器**进入 OperationEnabled 的瞬间开始使用 `0x607A`**，而那个值是过时的。
若期间轴实际位置变了（重力下沉、手动推过），会**朝旧目标走一次不受控的位移**。
不会"飞"（驱动器自身速度/转矩限幅在），但会"跳"。

`cancel_motion()` 对位置模式轴没有保护——它清的是 `pos_dirty` 和速度目标，
不碰已下发的 `target_pos`。

**修法**：在 `DS402_STEP_ENABLE_OP` 那一支也置 `preset_target = 1`。
代价为零，且**不会吃掉上层指令**——HAL 的顺序是 `begin`（预置）→ 业务代码
`write_pos`（暂存新目标）→ `commit`（写新目标），commit 会覆盖预置。

**为什么现在不改**：这是**安全关键路径上的行为变更**，且与旧 RT 不一致，
只有上机才能验证"使能瞬间不产生位移"。

**上机判据**：急停 → 手动把轴推离原位 → 恢复使能，观察轴是否朝急停前的目标移动。
